<objective>
Build browser-side smart polling so connected browsers silently receive standings updates without manual page refresh. An API route returns the latest data timestamp and match-window status, a custom React hook polls it at adaptive intervals, and the LeagueTableWrapper integrates both to auto-refresh the table when data changes.

Purpose: Without browser polling, users must manually reload the page to see updated standings after a match completes. Smart polling closes the loop: server detects changes (Plan 06-01/02), browser detects the change timestamp, and the UI silently refreshes.

Output: Working auto-refresh on the league table page with adaptive polling intervals and a subtle data freshness indicator.
</objective>

  <action>
  **1. Create `src/app/api/updates/check/route.ts`:**

  This is the endpoint browsers poll. It must be fast and cheap (DB query only, no external API calls).

  ```typescript
  export const dynamic = "force-dynamic"; // Never cache
  ```

  Export `GET(request: Request)`:
  - Parse `leagueSlug` and `season` from URL search params.
  - If missing, return 400 with `{ error: "Missing leagueSlug or season" }`.
  - Query the `standings` table: get the MAX `updatedAt` for the given league+season. Join with `leagues` table to resolve slug to league ID.
  - Query the `fixtures` table: check if any fixture for this league has `status` in live statuses (live, first_half, halftime, second_half, extra_time, penalties) AND kickoff within last 3 hours. This determines `matchWindowActive`.
  - Return JSON: `{ updatedAt: string | null, matchWindowActive: boolean }`.

  This endpoint does NOT use `isMatchWindowActive()` from fixture-window.ts (which checks ALL leagues). Instead, it checks match window for the SPECIFIC league the user is viewing. This is more precise.

  **2. Create `src/lib/hooks/use-polling.ts`:**

  "use client" directive at top.

  ```typescript
  interface UsePollingOptions {
    leagueSlug: string;
    season: string;
    onUpdate: () => void;           // Called when data changes
    matchWindowInterval?: number;   // ms, default 30_000
    offPeakInterval?: number;       // ms, default 300_000
    enabled?: boolean;              // default true
  }

  interface UsePollingReturn {
    lastUpdated: string | null;     // ISO timestamp for DataFreshness
    isMatchWindow: boolean;         // Whether matches are currently active
  }
  ```

  Implementation:
  - Use `useRef` for `onUpdate` callback to prevent stale closures (update ref on every render).
  - Use `useRef<string | null>` for `lastUpdatedRef` to track previous value without triggering re-renders.
  - Use `useState` for `lastUpdated` (exposed for DataFreshness) and `isMatchWindow` (exposed for UI).
  - Use `useRef<ReturnType<typeof setInterval>>` for interval ID.
  - `poll` function (wrapped in `useCallback` with `[leagueSlug, season]` deps):
    - Fetch `/api/updates/check?leagueSlug={slug}&season={season}`.
    - On success: update `isMatchWindow` from response.
    - If `updatedAt` differs from `lastUpdatedRef.current` AND `lastUpdatedRef.current` is not null (skip first poll): call `onUpdateRef.current()`.
    - Always update `lastUpdatedRef.current` and `setLastUpdated`.
    - On error: silently ignore (don't break the interval).
  - `useEffect` with deps `[enabled, isMatchWindow, matchWindowInterval, offPeakInterval, poll]`:
    - If not enabled, return.
    - Call `poll()` immediately on mount.
    - Set interval with `isMatchWindow ? matchWindowInterval : offPeakInterval`.
    - Return cleanup that clears interval.
  - **Critical:** When `leagueSlug` or `season` changes, the `poll` callback changes (new `useCallback`), which triggers the `useEffect` cleanup and restart. This means polling resets on league change -- correct behavior.
  - Also reset `lastUpdatedRef.current = null` when league/season changes to avoid false "update detected" on first poll of new league. Do this in a separate `useEffect` with deps `[leagueSlug, season]`.

  Return `{ lastUpdated, isMatchWindow }`.
  </action>

No additional wiring is needed -- the key-based remount strategy works because the data fetching is driven by useEffect on mount, not by server-side rendering.
