<objective>
Build the server-side match polling pipeline: an api_call_log table for budget tracking, shared status mapping utilities extracted from the seed code, fixture-window-aware polling logic, and a QStash-triggered cron route handler that polls API-Football only when matches are active.

Purpose: This is the backbone of the live data pipeline. Without automatic polling, data goes stale the moment a match starts. Fixture-window awareness prevents burning through the 100 calls/day free tier budget on quiet days.

Output: Working cron endpoint that QStash can trigger, which intelligently checks for active matches and polls API-Football for updates. All API calls are logged for budget visibility.
</objective>

  **1. Create `src/lib/pipeline/fixture-window.ts`:**
  - `getActiveLeagues(): Promise<ActiveLeague[]>` where `ActiveLeague = { leagueDbId, leagueApiId, leagueSlug, season, activeFixtureIds: number[] }`
  - Query fixtures table: kickoff within last 3 hours OR next 3 hours, AND status NOT in terminal states (finished, cancelled, postponed). Join with leagues to get apiId and slug.
  - Group results by league.
  - `isMatchWindowActive(): Promise<boolean>` -- thin wrapper, returns getActiveLeagues().length > 0. Used by browser polling endpoint.

  **2. Create `src/lib/pipeline/poll-active-matches.ts`:**
  Main polling orchestrator function:
  ```
  export async function pollActiveMatches(): Promise<PollResult>
  ```
  Steps:
  a. Call `canMakePipelineCall()` -- abort if budget exceeded, return early result.
  b. Call `getActiveLeagues()` -- if empty, return `{ polled: false, reason: 'no_active_matches' }`.
  c. For each active league:
     - Build team apiId -> dbId map by querying teams table for that league.
     - Call API-Football `/fixtures` with `league={apiId}&season={season}` via a NEW `ApiFootballClient` instance (with cache disabled or very short TTL like 60s for pipeline use). Use `withRetry()` wrapper.
     - Log the API call via `logApiCall()`.
     - For each fixture in the response:
       - Map status using shared `mapStatus()`.
       - Compare with DB status (query fixture by apiId).
       - If status changed: upsert fixture using the same `onConflictDoUpdate` pattern from seed-fixtures.ts.
       - If status transitioned TO "finished": add to `completedFixtures` array for match-completion chain (Plan 06-02 will implement `handleMatchCompletion`; for now, just collect and log them).
     - Return `PollResult` with counts: `{ polled: true, leaguesChecked, fixturesUpdated, matchesCompleted: completedFixtureIds[] }`.

  IMPORTANT: The `ApiFootballClient` constructor in `client.ts` requires an API key. For the pipeline, create the client with `process.env.API_FOOTBALL_KEY` (same env var the seed uses). Set `useCache: false` since we want fresh data. Keep the existing rate limiter to respect API limits.

  **3. Create `src/app/api/cron/poll-matches/route.ts`:**
  ```typescript
  import { verifySignatureAppRouter } from "@upstash/qstash/nextjs";
  import { pollActiveMatches } from "@/lib/pipeline/poll-active-matches";

  export const maxDuration = 60;

  async function handler(req: Request) {
    const result = await pollActiveMatches();
    return Response.json(result);
  }

  export const POST = verifySignatureAppRouter(handler);

  // Dev-only GET handler for manual testing
  export async function GET(req: Request) {
    if (process.env.NODE_ENV !== "development") {
      return new Response("Not allowed", { status: 403 });
    }
    const result = await pollActiveMatches();
    return Response.json(result);
  }
  ```
