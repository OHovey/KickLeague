    **src/lib/api-football/cache-proxy.ts:**
    Implement the CacheProxy class following the RESEARCH.md code example with these specifics:
    - Constructor takes `cacheDir` (string, default `.cache/api-football`) and `defaultTtlMs` (number, default 24 hours)
    - `hashKey(key: string)`: SHA-256 hash of the key string
    - `filePath(key: string)`: Uses first 2 chars of hash as subdirectory to avoid flat directory with thousands of files. Path: `{cacheDir}/{hash[0:2]}/{hash}.json`
    - `get(key: string): Promise<string | null>`: Read file, parse CacheEntry JSON, check if `Date.now() - entry.timestamp > entry.ttlMs` -- return null if expired, return `entry.data` if valid, return null on any fs error (cache miss)
    - `set(key: string, data: string, ttlMs?: number): Promise<void>`: Create directory recursively, write CacheEntry JSON with `{ data, timestamp: Date.now(), ttlMs: ttlMs ?? this.defaultTtlMs }`
    - `clear(): Promise<void>`: Remove entire cache directory (for development convenience)
    - `buildCacheKey(endpoint: string, params: Record<string, string>): string`: Deterministic key from endpoint + sorted params. Format: `{endpoint}?{key1=val1&key2=val2}` with params sorted alphabetically.
    - Export the class and the `buildCacheKey` helper (so the client can build keys before calling get/set)

    **src/lib/api-football/rate-limiter.ts:**
    - Import `RateLimiter` from `limiter`
    - Export a `createRateLimiter()` factory function that returns a RateLimiter configured for API-Football free tier: 10 tokens per minute interval
    - Export a `DailyQuotaTracker` class that:
      - Tracks `remaining` (initialized to 100) and `limit` (100)
      - Has `updateFromHeaders(headers: Headers)` method that reads `x-ratelimit-requests-remaining` and `x-ratelimit-requests-limit` from response headers
      - Has `canMakeRequest(reserveForCritical: number = 10)` method that returns false if remaining <= reserveForCritical (reserving quota for critical operations per CONTEXT.md)
      - Has `getRemainingDisplay()` returning a string like "85/100 daily requests remaining"
  </action>

    **src/lib/api-football/types.ts:**
    Define Zod schemas for all API-Football response types needed for seeding. Use `z.object()` with `.passthrough()` on outer wrappers (so extra fields don't cause validation failures). Key schemas:

    - `apiResponseSchema<T>`: Generic wrapper -- `{ get, parameters, errors, results, paging: { current, total }, response: T[] }`
    - `leagueResponseSchema`: League info with seasons and coverage data
    - `teamResponseSchema`: Team object with `team.id`, `team.name`, `team.code`, `team.logo`, `team.country`, `venue.name`, `venue.city`
    - `standingsResponseSchema`: League standings with `league.standings[][]` -- each entry has `team`, `points`, `goalsDiff`, `all`, `home`, `away`, `form`, `rank`, etc.
    - `fixtureBasicResponseSchema`: Fixture with `fixture.id`, `fixture.date`, `fixture.status`, `league`, `teams.home/away`, `goals`, `score`
    - `fixtureDetailedResponseSchema`: Same as basic plus `events[]`, `statistics[]`, `lineups[]`, `players[]`
    - `playerSquadResponseSchema`: Team squad with `players[]` each having `id`, `name`, `age`, `number`, `position`, `photo`
    - `playerStatsResponseSchema`: Player with stats including `games`, `goals`, `assists`, `cards`, etc.

    For every schema: use `.optional()` or `.nullable()` liberally on fields that may be missing. API-Football returns null for many fields. The partial accept pattern means schemas should be permissive.

    Export inferred TypeScript types using `z.infer<typeof schema>` for each.

    **src/lib/api-football/client.ts:**
    Implement `ApiFootballClient` class following the RESEARCH.md pattern:

    Constructor:
    - Takes `apiKey: string` and optional `options: { cacheDir?, cacheTtlMs?, useCache? }`
    - Creates CacheProxy instance (from cache-proxy.ts)
    - Creates RateLimiter instance (from rate-limiter.ts)
    - Creates DailyQuotaTracker instance
    - Stores `baseUrl` from endpoints.ts

    `async get<T>(endpoint: string, params: Record<string, string>, schema: z.ZodSchema<T>): Promise<T>` method:
    1. Build cache key using `buildCacheKey(endpoint, params)`
    2. If cache enabled: check cache. If hit, validate with `schema.safeParse()`, return data on success. On validation failure of cached data, log warning but still return the cached data (don't re-fetch just because schema evolved).
    3. Check `dailyQuota.canMakeRequest()`. If false, throw a descriptive error with remaining quota info.
    4. Await `rateLimiter.removeTokens(1)`. If blocked, log with chalk: "Rate limited, waiting..." with the endpoint being requested.
    5. Fetch from `${baseUrl}${endpoint}?${params}` with header `x-apisports-key: {apiKey}`
    6. Update daily quota from response headers
    7. If response not ok, throw with status and body
    8. Parse JSON, validate with `schema.safeParse(json)`
    9. On safeParse success: cache the raw JSON string, return parsed data
    10. On safeParse failure: log Zod validation warnings (issues summary, not full dump), cache the raw JSON anyway, return the raw JSON cast to T (partial accept pattern -- don't lose data due to schema mismatch)

    `getDailyQuotaStatus(): string` method: Returns quota display string.

    Export the class.

    **Important anti-patterns to avoid:**
    - Do NOT use `schema.parse()` (throws). Always use `safeParse()`.
    - Do NOT log every successful request. Only log errors and warnings (per CONTEXT.md).
    - Do NOT hardcode any league IDs in client.ts -- those belong in endpoints.ts.
    - The client should be completely unaware of the database. It fetches and validates -- that's it.
